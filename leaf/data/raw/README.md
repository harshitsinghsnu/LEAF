## Vocabulary extension (RQ6) — real reagents beyond the 1,200 labeled lipids

The original AGILE labeled set is a full factorial 20×12×5 = 1,200 design
with zero missing combinations — meaning `|X|` (the enumerable fragment
space) exactly equaled the labeled set, and RQ6's "B << |X|" condition for
a genuine budget-constrained search problem could not hold (see git
history / research plan for the original, honest disclosure of this
limitation).

**Fix**: AGILE's own repository also publishes a real, unlabeled virtual
candidate library of 12,276 lipids (`data.zip` →
`candidate_set_smiles_plus_features.csv`, same MIT license), generated by
the same Ugi-3CR reaction. `leaf/fragments/vocabulary.py::decompose_lipid`
(the exact inverse of `assemble_lipid`, validated at 1200/1200 exact
round-trip against the known labeled set) recovers each candidate's
(A, B, C) triple:

- 12,276/12,276 candidates (100%) decomposed successfully
- 9 new real A (amine) values, 62 new real B (aldehyde), 9 new real C (isocyanide) beyond the original 20/12/5
- Extended component lists are freely recombined (`fragments/vocabulary.py::component_lists`), since the Ugi-3CR reaction applies uniformly to any (amine, aldehyde, isocyanide) triple — this is the same published reaction applied to a broader real reagent pool, not a restriction to only the specific cross-combinations AGILE happened to screen, and not a fabricated reagent
- Resulting `|X|` = 29 × 74 × 14 = **30,044** (validated: 100% RDKit round-trip on the full enumerated space, `test_vocabulary.py::test_full_vocabulary_round_trips`)
- **Only the original 1,200 lipids have real experimental labels.** The other 28,844 combinations are real, chemically legitimate, assemblable structures with NO label — `O_GT` is fit only on the 1,200 and must genuinely extrapolate to score anything else. This is what finally makes B/|X| meaningful (e.g. 80/30044 ≈ 0.27% at E2's reduced budget).
- Checksum: `leaf/data/raw/agile_extended/candidate_triples.json` SHA-256 = `4f1dad06df75fed1ff5942d81c5dfe12e4408f509b439160c22c9555b4d92bea`

## Toxicity signal (§3.4/§5.9) — no real toxicity assay in this dataset

**AGILE contains no cytotoxicity or viability assay.** Both `expt_Hela`
and `expt_Raw` are transfection-efficiency readouts (in two different cell
lines), not safety/toxicity measurements. Rather than mislabel one of them
as "toxicity" (`expt_Raw`, in a macrophage line, might tempt a
safety-relevant framing, but it is still a luciferase transfection signal,
not a viability or immunogenicity assay), the toxicity signal used
throughout this project is the RDKit **toxicophore substructure match**
already implemented in `agents/verifier.py::toxicophore_flag` — a
deterministic, literature-derived structural-alert rule, not a learned or
wet-lab-measured toxicity label. This is disclosed explicitly:
- Dataset: none (no wet-lab toxicity assay backs this project's toxicity signal)
- Signal: RDKit substructure matching against a curated toxicophore SMARTS list (extend `TOXICOPHORE_SMARTS` in `agents/verifier.py` with a literature-curated set before treating hit rates as meaningful)
- This is a real, reproducible, disclosed heuristic — not a fabricated label — but it is not equivalent to a measured toxicity endpoint, and any coverage/calibration claim in E4 should be read with this caveat.
- Never touched by O_AL training or the main acquisition loop; used only by the Verifier layer.

## Tropism proxy (§5.6/§5.9)

State explicitly whether any organ-selectivity data source is confirmed.
Default assumption, absent confirmation: **no genuine tropism dataset is
available**, and any tropism score used is a heuristic proxy built from
known structure→organ rules. If so, tropism is reported outside the
primary hypervolume (§5.6), never as a fourth optimization axis, and any
Hypothesis-Agent "discovery" of a structure–tropism rule is disclosed as
recovering the proxy's own construction rather than a genuine finding.

## Label harmonization log (§5.8)

Only one real source (AGILE) is used, so no cross-source harmonization
(rank-normalization, source-indicator feature) is currently needed —
§5.8's harmonization step becomes relevant only if a second real potency
source (e.g. a released LUMI-lab dataset, E8) is added later. See
`leaf/data/processed/agile_harmonized.csv`, produced by
`scripts/build_real_data.py`, for the frozen, checksum-logged dataset
actually used to fit `O_GT`.
